# 调研与设计依据

这份文档把前期调研的结论整理成一张对照表：每条调研发现导出了哪个设计决定，以及这个决定现在验证到了哪一步。

## 结论先行

- **Defold 适合做小游戏适配，而且比 Godot 省一步。** 官方 HTML5 引擎没有用到 SIMD、线程和 WebAssembly 异常，可以原样使用，不需要像 godot_for_minigame 那样自己编译引擎模板。
- **现有的社区方案不能直接拿来用。** 它们依赖冻结的加载器副本和精确字符串替换，Defold 一升级就失效，而且没有平台接口。本项目沿用它们验证过的思路，换了一套不依赖具体版本文本的做法。
- **真实引擎已经在微信开发者工具里跑通。** 启动、渲染、触摸、存档、声音和 Lua SDK 都验证过。抖音和 TikTok 的开发者工具、以及所有真机还没有数据，这是现在最大的未知项。

## 调研发现与设计决定

| # | 调研发现 | 设计决定 | 验证状态 |
|---|---|---|---|
| 1 | Defold 官方 `wasm-web` 引擎除了一个 DataCount 段（属于 bulk memory 提案）之外没有用到 MVP 以外的特性，没有 SIMD、线程、异常 | 直接转换官方 HTML5 包，不做自定义引擎模板；导出时逐函数解码引擎二进制，发现被拦截的特性就拒绝导出 | 对 1.14.0、1.14.1 官方引擎实测通过 |
| 2 | 社区工具 dw 用自带的 `dmloader.js`（固定在 Defold 1.11.0）覆盖工程生成的那份 | `dmloader.js` 和引擎胶水都用工程自己的，原样保留 | 对两个版本的真实加载器测试通过 |
| 3 | dw 靠精确字符串替换把 `var FS=`、`var Module=` 改挂到全局对象上，引擎输出格式一变就失效 | 把两个文件按顺序放进同一个函数作用域，跨文件的全局变量自然互相可见，不需要改写 | 模拟宿主测试通过；真实引擎在微信开发者工具里运行通过 |
| 4 | 小游戏禁用 `eval` 和 `new Function`，Defold 的 `html5.run()` 底层正是 `eval` | 引擎里只有一处 `eval`，导出时把它改接到一个只接受 JSON 命令的桥上；Lua 侧提供 `minigame` 模块 | LuaJIT 对接真实 JS 桥联调通过；真实引擎里 API 功能测试的自动项全部通过 |
| 5 | dw 每次启动先删掉用户目录里的归档再重写，用来绕开“改了逻辑不生效” | 归档每次从包里读进内存，和浏览器里的路径一致；只有存档进持久存储 | 模拟宿主测试通过；真实游戏归档在微信开发者工具里加载通过 |
| 6 | Defold 的存档走 Emscripten IDBFS，依赖 IndexedDB，小游戏没有 | 实现 IDBFS 用到的那一小部分 IndexedDB 接口，数据落到宿主存储，引擎自己的存档代码不用改 | 模拟宿主里存档、重启、恢复、删除通过；真实引擎的 `sys.save()` 在微信开发者工具里重启三次都能读回 |
| 7 | TikTok 上写文件系统和 `getStorageInfoSync` 可能让客户端退出（godot_for_minigame 的真机经验） | TikTok 的存档走键值存储；Lua 桥屏蔽这几个接口 | 模拟宿主验证了“不调用”；真机未验证 |
| 8 | TikTok 上“每块新建 AudioBuffer 和 BufferSource”的播放方式让客户端崩溃过，而 Defold 的混音器正是这样播放 | TikTok 默认不给引擎提供 AudioContext，引擎会静音运行；提供 `minigame.inner_audio()` 和 `--assets` | 模拟宿主验证了降级路径；真机未验证 |
| 9 | 三个平台主包上限都是 4 MB，总包 20 到 30 MB | 引擎二进制（Brotli 压缩）和归档放进 `engine` 分包，主包只留约 0.42 MB 的胶水和运行时；导出时按平台上限检查 | 自动化测试通过 |
| 10 | 微信只上传白名单扩展名，`.arcd` 等不在名单里 | 归档分片统一加 `.bin` 后缀 | 自动化测试通过 |
| 11 | 微信官方通用引擎适配方案只支持 Emscripten 3.1.10 和 3.1.51，Defold 用 4.0.6 | 不依赖官方转换工具 | 不适用 |
| 12 | iOS 15.0、15.1 的 WebGL2 基本不可用；Defold 自己按 User-Agent 在 iOS 15.2 以下改用 WebGL1 | 用宿主的系统信息拼出 User-Agent，让引擎自带的回退逻辑生效 | 模拟宿主测试通过。真实运行发现了一个反例：微信开发者工具上报的是所模拟机型的系统版本（iOS 10.0.1），引擎因此退回 WebGL 1 而没有着色器可用；现在对开发者工具不再拼系统版本 |
| 13 | dw 没有键盘输入 | 接管引擎对画布 `contentEditable` 的写入，打开宿主键盘，把文本差异还原成按键事件 | 模拟宿主测试通过，真实输入法未验证 |
| 14 | TikTok 宿主同时暴露 `wx`、`tt` 别名，且 `GameGlobal` 不是全局对象 | 引擎需要的浏览器对象全部作为作用域变量绑定，不往全局写任何东西 | 模拟宿主测试通过；真实引擎在微信开发者工具里运行通过 |
| 15 | godot_for_minigame 的导出事务和所有权清单在三个平台上用过 | 沿用：暂存目录、清单、锁、失败回滚、只替换自己拥有的路径 | 自动化测试通过 |
| 16 | 调研时没有任何公开的性能实测数据 | 支持矩阵按验证层级如实标注，不把“模拟宿主通过”写成“已支持” | 持续执行 |

## 调研之后才发现的事

**Defold 1.14.1 重写了加载器。** 开发期间 Defold 发布了 1.14.1，`dmloader.js` 的启动流程从“各个回调都去调用 `_preloadAndCallMain()`”改成了由 `GameStartup` 统一编排的会话式设计，平台层也从 `GLFW` 改名为 `DefoldPlatform`。导出工具的结构检查按预期拦下了这个版本，随后运行时增加了第二条启动路径。

这件事印证了调研里对 dw 的判断：绑定某个版本的加载器文本是不可持续的。它也说明本项目的做法仍然有版本耦合，只是耦合点从“文本逐字相同”缩小到了“加载器对外的几个成员还在”，并且变化时会在导出阶段报错，而不是到真机上才发现。

**真实引擎第一次运行，暴露了四件模拟宿主测不出来的事。** 在微信开发者工具里跑真实引擎之前，全部测试都是绿的；跑起来之后依次遇到：

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动时报 `canvas.style.removeProperty is not a function` | 引擎第一次交换缓冲时通过 `style.setProperty()` 调整画布尺寸，引擎替身没有模拟这一步 | 适配层的样式对象补上这几个方法；替身逐句照搬 Emscripten 调整画布的代码 |
| 引擎报 `Unable to get a valid shader` 后退出 | 微信开发者工具上报的是所模拟机型的系统版本（iOS 10.0.1），拼进 User-Agent 后引擎退回了 WebGL 1 | 宿主平台是开发者工具时不再拼系统版本 |
| GUI 回调报 `Node used in the wrong scene` | Defold 1.14.1 默认让所有脚本共用一个 Lua 环境，游戏对象脚本轮询时把 GUI 脚本的回调也派发了 | SDK 记下每个回调属于哪个脚本，谁轮询就只派发自己的；不同 Lua 环境之间用桥分配的名字区分 |
| 测试结果在控制台里看不到 | 引擎的 release 版丢弃 `print()` | 增加 `minigame.log()`，SDK 自己的警告也改走宿主控制台 |

四个问题都是先让测试复现、再修的。它们也说明了引擎替身的边界：替身只能模拟已经知道的引擎行为，真实运行这一关省不掉。

## 还没回答的问题

| 问题 | 为什么重要 | 怎么回答 |
|---|---|---|
| 真实引擎在抖音、TikTok 里能不能启动 | 微信开发者工具已经通过，另外两个平台还没有数据 | 把 API 功能测试应用导出到这两个平台，在抖音开发者工具和 `ttmg dev` 里各跑一遍 |
| 真机上的表现 | 开发者工具的模拟器是桌面浏览器内核，和手机上的运行时不是一回事 | 用同一个测试应用在 iOS 和 Android 真机上预览 |
| 帧率、内存、启动时间 | 决定 Defold 相对 Cocos Creator 有没有实际优势 | 同一个压力场景在真机上对比 |
| TikTok 上引擎混音器到底会不会崩溃 | 现在的“默认关闭”是从 Godot 的经验类推来的 | 用 `--engine-audio on` 在真机上试 |
| 带 JS 库的原生扩展能不能用 | 很多 Defold 扩展带 JS 代码 | 挑一个常用扩展实测 |
| 抖音和 TikTok 的上传白名单 | `--assets` 的警告目前只按微信的名单判断 | 查各平台文档或实测上传 |

## 和 godot_for_minigame 的关系

两个项目解决的是同一类问题，结构上有意保持一致：同样的三个平台、同样的 `PlatformRuntime` 提供者选择、同样的导出事务、同样以 `support-matrix.json` 为唯一事实源。主要差别来自引擎本身：

| | godot_for_minigame | defold_for_minigame |
|---|---|---|
| 引擎 | 自己编译的单线程模板，随插件分发 | Defold 官方引擎，来自用户自己的 HTML5 包 |
| 版本绑定 | 引擎模板与编辑器版本精确匹配 | 检查加载器结构，不绑定版本号 |
| 导出入口 | Godot 编辑器插件 | 命令行工具 |
| 脚本侧 SDK | `MiniGameSDK`，225 个方法，逐个封装 | `minigame`，45 个函数，加通用透传 |
| 脚本与宿主的通道 | JavaScriptBridge | `html5.run()` 改接的 JSON 命令桥，每帧轮询 |
| 验证 | 开发者工具和真机都跑过 | 微信开发者工具跑过，另外两个平台和真机还没有 |
